# 모니터링과 반응속도

## 표시

- **세션별:** 사이드바 행과 터미널 제목에 `12% 340M`. 세션이 띄운 자식 프로세스까지 트리 전체를 합산한다.
- **PC 전체:** 상태줄 오른쪽에 `CPU 23% · RAM 9.7G/16.0G`. 70% 이상 노랑, 90% 이상 빨강(CPU와 RAM 중 큰 값 기준). 폭이 70칸 미만이면 숨긴다.
- **CPU 기준:** 전체 코어 대비 비율(작업 관리자와 같은 방식). 세션 값을 합치면 PC 전체 CPU를 넘지 않는다.
- **메모리 기준:** 프로세스별 작업 집합(working set) 합계. 공유 메모리는 중복 계산되어 작업 관리자 숫자와 조금 다를 수 있다.
- 첫 측정에서는 CPU 기준값이 없어 0%로 나온다. 두 번째 측정부터 정확하다.

## 구현

- 새 크레이트 없이 `windows-sys`만 쓴다: `GetProcessTimes`, `GetProcessMemoryInfo`, `GetSystemTimes`, `GlobalMemoryStatusEx`. 프로세스 트리는 기존 `descendant_pids`를 재사용한다.
- Windows가 아니면 측정 함수가 `None`을 돌려주고 표시도 나오지 않는다(빌드는 된다).
- 프로세스 트리 합산 중 자식이 종료되면 CPU 시간 합계가 줄 수 있다. 음수가 되지 않게 `saturating_sub`로 0 처리한다.
- 세션을 재시작한 직후 도착한 이전 프로세스의 결과는 PID가 달라서 버린다.

## 반응속도 설계

요구사항: CLI 반응속도와 사용감이 민첩해야 한다(작업 환경이 여러 터미널을 오가는 것이라 가장 중요).

| 측정/결정 | 값 |
|---|---|
| `measure()` 한 번(세션 1개, 프로세스 약 440개, 디버그 빌드) | 약 17~20ms (3회: 19.6, 20.6, 17.2ms) |
| 측정 주기 | 2초 |
| 측정 위치 | 전용 스레드. UI 루프는 `try_recv`로 논블로킹 수신만 함 |
| 측정이 느릴 때 | 이전 요청이 안 끝났으면 다음 요청을 보내지 않고 건너뜀 |
| 이벤트 대기 | `event::poll` 10ms. 키 입력은 즉시 깨우고 자식 출력은 최대 10ms 지연 |
| 유휴 재그리기 | 실행 중인 세션이 있을 때만 약 30ms 주기. 측정 결과 도착 시 한 번 |

세션이 여러 개면 세션마다 프로세스 스냅샷을 따로 뜨므로 비용이 세션 수에 비례한다. UI 스레드에서 했다면 2초마다 눈에 띄는 끊김이 생겼을 것이어서 처음부터 스레드로 분리했다.

## 알려진 병목과 해결 현황

- 세션 정지/삭제 때 `Drop`에서 하는 프로세스 트리 종료는 개별 정지 시 백그라운드 스레드(`thread::spawn`)로 옮겼고, 앱 전체 종료(`shutdown_all`)에서는 프로세스 스냅샷을 1회만 떠서 모든 세션 트리를 일괄 종료한다.
- 화면을 그릴 때 인접한 동일 스타일 셀을 하나의 `Span`으로 묶고, 세션 화면이 변하지 않은 프레임(스피너 틱 등)에는 `RenderCache` 버퍼를 재사용한다.
- 상태 감지(`refresh_screen_flags`)는 전체 화면 대신 하단 12줄만 읽으며 최대 100ms 주기로 쓰로틀링한다.
- 전체 시작(`start_sessions`)은 `thread::scope`로 병렬 spawn하여 지연을 줄였다.
